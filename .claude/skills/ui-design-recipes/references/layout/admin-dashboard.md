# 業務用の管理画面

> **いつ読むか**: 一覧・絞り込み・設定など「読む・操作する」業務画面を作るとき（チャット・対話画面には適用しない）
> **前提**: なし（本レシピは `foundations/` のトークンとは別体系。§2 参照）
> 色は Tailwind の既定色クラス（`gray` / `emerald` / `blue` / `red` / `amber` 等）の役割名で書く。HEX 値は使わない。

## 1. 要点

- 対話体験の面（`foundations/` の役割ベーストークン）と、業務用の管理画面は**デザイン言語を統一しない**。管理画面は Tailwind の既定色パレットをそのまま使う（§2）。
- アクセント色は **4 系統に固定**する: 緑＝状態・選択・ナビゲーション／青＝フォームの主要送信／赤＝破壊的操作／黄＝注意喚起（断定しない）。新しい色を足さず、この 4 系統の中で表現する。
- 注意・警告を表す色（黄・赤）は、**カードやセクションのような大きな面では背景を塗らず、枠線と数字・文字の色だけに留める**。過度な切迫感や「診断された」印象を与えないため。バッジのような小さな面は、最も淡い段（50）の面＋濃い文字でよい。
- シェルは「sticky ヘッダー＋ sticky サイドナビ＋本文」の 3 段。本文コンテナの最大幅は画面の性質（一覧・ダッシュボードか、単票・フォームか）で 2 区分にする。
- 一覧は sticky thead ＋行全体クリックのテーブルが基本形。グラフは依存を足さず自前の SVG で描く。

## 2. なぜ別体系にするか

管理画面は「一覧を読み、絞り込み、設定する」ための**道具**であり、対話体験の面は「主役と話す」**体験**である。情報密度・操作の性質・求められる情緒が異なるため、同じトークン（角丸・影・グラデーション・ブランドカラー）を当てると、業務画面が体験寄りの意匠に引きずられて読み取りやすさを落とす。

| 面 | 色の出どころ |
| --- | --- |
| 対話体験の面 | 役割ベースのセマンティックトークン（`foundations/` 群） |
| 業務用の管理画面（本レシピ） | Tailwind 既定色（`gray` / `emerald` / `blue` / `red` / `amber` / `purple` / `sky` 等） |

- 管理画面の実装に `foundations/` 由来のトークン（面のグラデーション・ブランドカラー等）を持ち込まない。逆に、本レシピの値（Tailwind 既定色・角丸の数値）を対話面へ持ち出さない。
- **「揃える」ではなく「別の面として運用する」が結論。** 同じアプリの中で色の出どころが 2 系統あることは不整合ではなく、対象が違うことの表れとして扱う。

## 3. 色の役割を 4 系統に固定する

| 系統 | 役割 | 使う場面の例 | Tailwind 既定色の例 |
| --- | --- | --- | --- |
| **緑** | 状態・選択・ナビゲーション（いま何が選ばれているか） | サイドナビの選択中項目・絞り込みプリセットの選択中・処理が済んだことを示す帯・ホバー時の行動ラベル | `emerald-50/500/600/700` |
| **青** | フォームの主要送信ボタン（押すと保存・送信が起きる） | 「保存する」「招待する」等の主操作ボタン | `blue-600`（hover は `blue-700` 等 1 段濃く） |
| **赤** | 破壊的操作／警告のトーン | 「削除する」等の取り消せない操作。警告は KPI カードの枠と数字・状態バッジに限る（大きな面は塗らない） | `red-600`（操作）・`red-300` の枠と `red-700` の文字（警告） |
| **黄** | 注意喚起（断定しない） | 中間的な状態の帯・注意を促す KPI のトーン・変化の「下向き」 | `amber-500/600`・枠 `amber-300`・文字 `amber-700`（面を塗るのは告知の帯やバッジの `amber-50` まで） |

- **本文・枠線・見出し等の基本トーンはこの 4 系統に含めない。** 通常のテキスト・境界線は中立のグレー階調（`gray-400`〜`gray-800` 等）を使い、4 系統は「意味を持たせたいアクセント」だけに使う。
- **新しい色を足さない。** 一見バラバラに見える配色（例: あるボタンだけ青）も、上表のどの役割に当たるかで説明できるなら是正しない。「役割ごとに系統が決まっている」ことを優先し、「見た目を全部同じ色に揃える」ことを目的にしない。
- 上表以外の色（紫・インディゴ・スカイ等）を使う場合は、**4 系統のどれにも属さない中立的な分類ラベル**（プランの種別・活動の種類など、状態や評価を伴わない属性値）に限る。評価や状態を意味する箇所に新しい色相を割り当てない。

## 4. シェル（ヘッダー・サイドナビ・本文）

```
<header class="sticky top-0 z-40 bg-white border-b border-gray-200">…</header>
<div class="flex">
  <aside class="hidden md:flex w-60 shrink-0 sticky top-[ヘッダー高] …">サイドナビ</aside>
  <section class="flex-1 min-w-0">本文</section>
</div>
```

| 項目 | 値 | Tailwind |
| --- | --- | --- |
| ヘッダー | sticky・最前面 | `sticky top-0 z-40 bg-white border-b border-gray-200` |
| サイドナビ幅（`md` 以上） | 240px | `w-60` |
| サイドナビ（`md` 未満） | 開閉メニュー（ハンバーガー起動） | — |
| 本文コンテナ（一覧・ダッシュボード系） | 最大幅 1152px | `max-w-6xl mx-auto px-6 py-8` |
| 本文コンテナ（単票・フォーム系） | 最大幅 768〜896px 程度 | 例: `max-w-3xl mx-auto px-6 py-8` |

- **本文コンテナの最大幅は画面の性質で 2 区分にする。** 横に列が並ぶ画面（表・KPI グリッド）は広め（`max-w-6xl`）、1 カラムの読み物・入力フォームは狭め（`max-w-3xl` 程度）にする。1 カラムのテキスト・入力欄は行が長く伸びるほど読みにくくなる（可読行長）ため、フォーム系まで一律に広げない。
- **ヘッダーと本文で、最大幅を当てる階層を揃える。** ヘッダー側だけ「余白の外側」に最大幅ラッパを置き、本文側は「余白の内側」に置く、のように階層がずれると、左端の位置が数 px 単位でずれる。両方とも「最大幅ラッパの内側に左右余白」という同じ構造にする。
- サイドナビの選択中項目は§3の緑系統（背景を淡く塗り、文字色を濃い緑にし、先頭に小さいドットを置く）で示す。

## 5. KPI カード

| 項目 | 値 | Tailwind |
| --- | --- | --- |
| 角丸 | 16px | `rounded-2xl` |
| 枠線（通常） | 中立グレー | `border-gray-200` |
| 枠線（注意） | 黄系統 | `border-amber-300` |
| 枠線（警告） | 赤系統 | `border-red-300` |
| 内側余白 | 16px | `p-4` |
| 数値の文字色（注意/警告） | 枠と対にした濃い色 | `text-amber-700` / `text-red-700` |

- **注意・警告のトーンでも背景は塗らない。** 変えるのは枠線の色と数値の文字色だけ。背景まで塗ると「危険を通知している」ように見えすぎて、業務ダッシュボードとしての落ち着きを損なう。
- **向きに良し悪しの意味が無い差分（件数の前週比など）は色分けしない。** 「増えた＝良い」とは限らない指標（例: フォローが必要な人数が増えるのは望ましくない）があり、色を付けると暗黙の評価を生んでしまう。矢印記号と数値だけで増減を示し、色は中立グレーのまま。
- **向きに意味がある変化（「最近の変化」の上向き／下向きなど）だけ色を付ける。** 上向きは緑、下向きは黄にし、**赤は使わない**（下がったことを「危険」と読ませない）。
- カードを遷移リンクにする場合、カード自体の見た目は変えず、ホバー時にポインタへ追従するラベル（「一覧で見る →」等）を重ねる。カード面積が小さいときは追従させず固定位置にする。作法の一次情報は `components/tooltip-and-hover-label.md` を参照する。

## 6. セクションカード

一覧のショートリストや、意味のまとまりごとに画面を区切る枠。

```
<section class="rounded-2xl border {ring} bg-white overflow-hidden">
  <div class="flex items-center justify-between gap-3 px-4 py-3 {headerBg}">
    <div class="flex items-center gap-2.5">
      <span class="flex h-8 w-8 items-center justify-center rounded-full {iconBg}">{icon}</span>
      <div><h2 class="text-sm font-semibold">{title}</h2><p class="text-[11px] text-gray-500">{subtitle}</p></div>
    </div>
    <span class="rounded-full px-3 py-1 text-base font-bold {badge}">{count}{unit}</span>
  </div>
  <div class="p-4">{children}</div>
</section>
```

| 項目 | 値 | Tailwind |
| --- | --- | --- |
| 角丸 | 16px | `rounded-2xl` |
| ヘッダー内の余白 | 左右16px・上下12px | `px-4 py-3` |
| 本文の余白 | 16px | `p-4` |
| アイコンの丸 | 32px | `h-8 w-8 rounded-full` |
| 件数バッジ | 丸ピル・大きめの文字 | `rounded-full px-3 py-1 text-base font-bold` |

- **枠・ヘッダー背景・アイコン背景・件数バッジの 4 か所をまとめて 1 つのアクセント（§3 のいずれか）に紐づける。** ばらばらに配色すると、同じセクション内でどれが同じ意味の強調なのか読み取れなくなる。
- 件数バッジは本文と同じ大きさの数字だと埋もれるため、丸バッジで独立させて強調する。

## 7. テーブル

```
<div class="bg-white rounded-2xl border border-gray-200 shadow-sm overflow-hidden">
  <div class="overflow-auto max-h-[70vh]">
    <table class="w-full text-sm">
      <thead class="sticky top-0 z-[15] [&_th]:bg-white [&_th]:shadow-[inset_0_-1px_0_0_var(--color-gray-200)]">
        <tr class="text-xs text-gray-500 text-left whitespace-nowrap"><th class="py-3 px-4 font-medium">…</th></tr>
      </thead>
      <tbody>
        <tr class="group relative border-b border-gray-100 last:border-0 hover:bg-{accent}-50/60">
          <td class="static py-3 px-4">
            <a class="relative z-10 …">行の本題（正規の遷移経路）</a>
            <a class="absolute inset-0" aria-hidden="true" tabindex="-1"><span class="sr-only">詳細</span></a>
          </td>
        </tr>
      </tbody>
    </table>
  </div>
</div>
```

- **`overflow-auto` の縦スクロールコンテナに `max-h` を与えて初めて `sticky top-0` が効く。** 高さの上限が無いテーブルは、そもそも内側で縦にスクロールしないため、`thead` の sticky がページスクロールに追従する挙動にならない。`max-h-[70vh]` のように上限を明示する。
- **列見出しの境界線は `<tr>` の下罫線ではなく `<th>` の内側影（inset shadow）で描く。** テーブルの既定スタイル（`border-collapse: collapse`）の下では、sticky なセルの通常の border が描画されないことがある。`shadow-[inset_0_-1px_0_0_...]` なら `collapse` の影響を受けない。
- **`<th>` に `bg-white` を明示する。** 既定では透明なので、sticky にした状態でスクロールすると下の行が透けて見える。
- **並び替えできる列見出しには、矢印を常に出す。** 効いている列の矢印だけを §3 の緑系統（例: `text-emerald-600`＋同系の淡い段の `text-shadow` でわずかに発光）にして並び順（↑/↓）を示し、効いていない列は中立グレーの矢印に留める。このグレーは白地で 3:1 以上の段（例: `text-gray-500`）にする（矢印が「押すと並ぶ」ことを示す唯一の目印なので、図形のコントラスト基準を下回る淡い段にしない）。矢印を効いている列にだけ出すと、見出しの文字は全列同じグレーなので、どれが押せるのか見分けられない。矢印は装飾として `aria-hidden` にし、状態は `aria-sort` で伝える。
- **列見出しは折り返さない（`whitespace-nowrap`）。** 表の自動レイアウトは幅が足りないと列を比例で縮めるため、見出しが単語の途中で割れる（和文は任意の文字間で折り返せるので特に目立つ）。縮める分は本文セルの折り返しで吸収させ、それでも収まらない幅はラッパの `overflow-auto` で横スクロールにする。見出しに矢印やアイコンを足すと必要幅が増えて、この割れが起きやすくなる。
- **`thead` の z 値は、行の中の「手前に出したい要素」より高く、他の重なり要素（絞り込みパネルなど）より低い値にする。** 行内に「クリック領域を広げる `absolute inset-0` のオーバーレイ」と「その手前に出す本題のリンク（`relative z-10`）」がある構成では、オーバーレイが `thead` と同じ段（例: 10）だと、スクロールで行が動いた瞬間に DOM 順の後勝ちで `thead` より前へ出てしまう。行内の値（例: 10）と他の重なり要素の値（例: 20）の**間**を `thead` に割り当てる（例: 15）と、両方の関係を崩さずに済む。
- **行全体を押せるようにするパターン**: 本題（メンバー名等）には通常の `<a>`／`<button>` を置いて正規の遷移経路にし、その上に `absolute inset-0` で行全体を覆う 2 個目の同じ遷移先のリンクを重ねる。2 個目は `aria-hidden="true" tabindex="-1"` にして読み上げ・タブ移動からは隠し、内部に `sr-only` のテキストだけ持たせる。マウスは行のどこを押しても遷移でき、キーボード・スクリーンリーダーは 1 個目の本題リンクだけを辿る。
- **空値は「—」で表す。** 空文字や `0` をそのまま出すと「未計測」なのか「実際に 0」なのか区別できない。値が無い列は常に同じ記号（「—」）に統一する。

## 8. フィルタ（3 段構成）

1. **検索**: 単発の入力欄（`w-56` 程度）。入力の反映は一定時間（数百 ms）遅らせ、1 打鍵ごとに絞り込みが走らないようにする。
2. **プリセット**: よく使う条件の組み合わせを 1 クリックで切り替える丸ピルの並び。選択中は§3 の緑系統（`bg-emerald-50 border-emerald-300 text-emerald-700`）、非選択は中立グレー。
3. **詳細パネル**: 個別の軸を組み合わせる折りたたみ式のパネル。**開閉トグルは見出し（`<h2>`）自体に置く**（開閉可能な領域であることが、装飾のボタンではなく見出しの構造として伝わるようにする）。パネルは白背景・枠線・軽い影で囲み、プリセット段と同じ高さ・書体の並びが単純に 2 段続くだけに見えないようにする。

続けて、**適用中チップ**の段を置く。効いている条件を「適用中: ○○ ×」の形で個別に外せるようにし、絞り込みの内容を常に可視化する。

- 詳細パネルは、初回表示時点で「プリセット段からは見えない条件」が既に効いていたら**開いた状態で出す**。閉じたままだと、隠れた条件で絞られていることに利用者が気づけない。
- 検索・プリセット・詳細パネル・適用中チップの「解除」など、複数の操作元が URL のクエリを書き換える設計では、直前の操作がまだ反映されていない間に別の操作が発火すると、互いの条件を上書きし合う競合が起きやすい。反映待ちの状態を 1 か所で共有し、後発の操作は「まだ反映されていない直前の状態」の上に重ねる。

## 9. 空状態

| 種類 | 見た目 | 解除の導線 |
| --- | --- | --- |
| データがまだ無い | 破線の枠＋中立グレーの文言 | 無し |
| 絞り込みで 0 件 | 同じ枠 | 「絞り込みを解除する」等の導線を添える |

```
<div class="rounded-2xl border border-dashed border-gray-300 bg-white px-6 py-12 text-center text-sm text-gray-500">
  <p>{message}</p>
  {action && <div class="mt-3">{action}</div>}
</div>
```

- **2 種類を専用の enum で分けず、「解除できる導線があるかどうか」だけで出し分ける。** 呼び出し側は自分がどちらの状況かを既に知っているため、種類のラベルを別に持たせると同じ情報を二重に判定することになる。
- アイコンは基本的に足さない。管理画面全体にアイコン体系が定まっていない場合、1 か所だけ絵文字やアイコンを入れると浮く。

## 10. 準備中の表示

未実装の画面には固定の文言と控えめな絵文字だけを置き、個別に作り込まない。

```
<div class="max-w-3xl mx-auto px-6 py-8">
  <h1 class="text-xl font-bold text-gray-800">{title}</h1>
  <p class="mt-1 text-sm text-gray-500">{description}</p>
  <div class="mt-6 rounded-2xl border border-dashed border-gray-300 bg-white px-6 py-12 text-center">
    <p class="text-3xl mb-2">🚧</p>
    <p class="text-sm text-gray-500">この画面は準備中です。</p>
  </div>
</div>
```

## 11. バッジ

- 種類ごとに **`{label, chip}` の対応表（Record）を 1 つ持ち**、表示は共通の `Pill` コンポーネント 1 つに集約する。バッジの見た目（角丸ピル・小さい文字）を種類ごとに作り分けない。

  ```tsx
  // 例: 手続き（処理）の状態。人を評価する分類ではない
  const PROCESS_META: Record<Process, { label: string; chip: string }> = {
    done: { label: "完了", chip: "bg-emerald-50 text-emerald-700 border-emerald-200" },
    waiting: { label: "確認待ち", chip: "bg-amber-50 text-amber-700 border-amber-200" },
    stopped: { label: "停止中", chip: "bg-gray-100 text-gray-600 border-gray-200" },
  };

  function Pill({ label, chip }: { label: string; chip: string }) {
    return (
      <span className={`inline-flex items-center px-2 py-0.5 rounded-full text-xs font-medium ${chip}`}>
        {label}
      </span>
    );
  }
  ```

- **人（利用者・従業員など）の状態を評価・断定するバッジを作らない。** 「良好」「要対応」「危険」のように人を格付けする語は、そのまま管理画面に転用されると断定的な評価になる。人を対象にする画面では、断定ではなく「可能性」として扱う語（「フォロー候補」「気になるサイン」など、プロダクトの表現ルールで許された語）にし、色も赤を避ける。
- 手続き・処理の状態を示すバッジ（完了／確認待ち／停止中 等）は §3 の 4 系統に沿わせる。ラベルは次の行動が分かる語にする。属性を示すだけのバッジ（分類名・種別ラベル等）は中立寄りの色（グレー・スレート等）や、4 系統に含まれない色相を割り当ててよい。
- 「●＋ラベル」の形で強調したいバッジは、丸のドットと文字色を同じ系統でそろえ、対象が存在しない（評価対象外等）場合は中立グレーの文字だけに落とす。

## 12. グラフ

- ライブラリを追加せず、**自前の inline SVG** で描く（`viewBox` で固定の論理サイズを持たせ、`className="w-full"` でコンテナ幅に合わせる）。折れ線・面・横棒など単純な形であれば、依存を増やすコストの方が大きい。
- グリッド線・軸ラベルの色は 1〜2 色の定数（例: グリッド用の薄いグレー、軸文字用のやや濃いグレー）に固定し、系列の色（データそのものを表す色）とは別に持つ。
- **グラフの色定数はバッジの配色（§11）と分けて持つ。** 同じ変数を共有すると、バッジの意味（状態）が変わったときにグラフの見た目まで意図せず変わってしまう。系列の色は「その指標を表す色」として独立に決める。
- 数値の増減に良し悪しの意味を持たせたくない指標（推移・トレンドの折れ線など）は**単色のまま**にする。区間ごとに色を塗り分けると、上がった／下がった各点に良し悪しの読みが生まれてしまう。状態を色で示したい場合（例: 実績値がしきい値を下回ったら警告色にする）だけ、明示的にしきい値と色の対応を持たせる。
- ポインタに追従して出す注釈・ラベルの実装は `components/tooltip-and-hover-label.md` を参照する。

## 13. 落とし穴

- **対話面の役割ベーストークンを管理画面に持ち込む。** 業務画面が対話体験寄りの意匠に引きずられ、一覧の読み取りやすさが落ちる。管理画面は Tailwind 既定色で完結させる（§2）。
- **注意・警告のトーンで背景まで塗ってしまう。** 過度な切迫感を与え、「診断された」ような読み方を誘発する。枠線と文字色だけに留める（§5）。
- **増減の色分けで暗黙の評価を持ち込む。** 向きに良し悪しの意味が無い指標まで機械的に緑／赤で塗ると、実態と逆の印象を与える。意味がある変化でも下向きに赤は使わない（§5）。
- **`sticky` な `thead` の z 値を、行内の重なり要素と同じ値にする。** DOM 順の後勝ちで、スクロール時に行の要素が見出しより前面に出てしまう（§7）。
- **空状態の 2 種類を enum で分けて、呼び出し側とも二重に判定してしまう。** 「解除の導線があるかどうか」だけで表現すれば足りる（§9）。
